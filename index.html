Enterprise Architecture

Two-Tier Zero-Update Deployment Architecture

This portal employs a zero-update client architecture designed for Ancilleo Sdn. Bhd. contact center operations. Agents run a tiny static launcher file (launcher.html) on their desktop, which embeds the core portal hosted on GitHub Pages (index.html) via an iframe.

Tier 1: Desktop Launcher (launcher.html)

  • • Lightweight standalone file kept on agent workstation desktops.
  • • Never requires re-distribution when operational workflows change.
  • • Includes connection watchdog, fallback offline banner, and auto-retry.

Tier 2: Cloud Hosted App (index.html)

  • • Deployed via GitHub Pages repository with continuous deployment.
  • • Changes pushed to GitHub immediately update all active agent desktops.
  • • Standalone client cache using localStorage / IndexedDB.

Production Backend Connectors (Supabase / Firebase / REST)

To transition this prototype to a centralized corporate database, simply replace the local storage provider in appStore with one of the production adapters below:

// Sample Supabase Client Initialization
import { createClient } from '@supabase/supabase-js'

const supabase = createClient('https://your-project.supabase.co', 'YOUR_PUBLIC_KEY')

// 1. Fetch live leaves & roster
export async function getLeaves() {
  const { data, error } = await supabase.from('ancilleo_leaves').select('*')
  return data || []
}

// 2. Submit medical claim with attachment stored in S3/Supabase Storage bucket
export async function submitClaim(claimRecord, fileBlob) {
  const filePath = `receipts/${Date.now()}_${fileBlob.name}`
  const { data: uploadData } = await supabase.storage.from('medical-claims').upload(filePath, fileBlob)
  const { data: urlData } = supabase.storage.from('medical-claims').getPublicUrl(filePath)
  
  return await supabase.from('ancilleo_claims').insert([{
    ...claimRecord,
    attachment_url: urlData.publicUrl
  }])
}
